## Verificación

**1. Que `isolate:true` realmente se aplica**
- `angular.json:133`: `runnerConfig: "vitest.config.mjs"`. No cambia nada más del target `test`.
- `executor.js:183-197` (`@angular/build` 21.0.6) pasa esa ruta como `config` a `startVitest`.
- En `plugins.js:96-130`, el valor predeterminado `isolate:false` (línea 101) se combina primero con el `test` del usuario (`mergeConfig(projectDefaults, {test: testConfig})`). Después solo se sobrescriben `name`, `include`, `browser`, `environment`, `plugins`, `optimizeDeps` y `resolve`. **Por eso `isolate:true` llega al proyecto que Angular construye.**
- Vitest 4.0.16 acepta `isolate` a nivel de proyecto.
- No se tocan workers, timeouts ni `node_modules`.
- `npm test` sigue siendo `ng test` (`package.json:12`).

**2. Que el aislamiento corrige la causa del arrastre**
- Antes, con `isolate:false`, los archivos de un mismo worker compartían el mismo módulo `TestBed`.
- Cuando una prueba se pasa del tiempo, Vitest ejecuta el `afterEach` de `init-testbed`, que reinicia el `TestBed`. Pero el cuerpo asíncrono de esa prueba sigue corriendo y puede volver a instanciar el módulo. Eso coincide con el error «already instantiated» en `legal-page`.
- Con `isolate:true`, cada archivo carga sus módulos desde cero, así que el arrastre se corta.

**3. Prueba de Admin** (`admin-dashboard.component.spec.ts:9-31`)
- `overrideComponent` deja `imports: []` y un template con las mismas expresiones que `admin-dashboard.component.html:185-186` (`moduloActivo()?.titulo` y `?.descripcion`).
- Se mantienen las cuatro aserciones (`[]`, `null`, `h1` vacío y `p` vacío), además de `detectChanges` y `match`. Así se cubre el hallazgo Bajo de `008-f4-m1-medicion`.

**4. P3 de booking**
- `booking.component.spec.ts:68-81` sigue `cargarStaffServicio` (`booking.component.ts:1027-1043`):
  - el `next` obsoleto se descarta por la guarda de sucursal/servicio (`:1036`), y `staffByService` sigue en `{}`;
  - la barrera sigue cerrada hasta que llega `complete` y el `finalize` (`:1033`) libera `staffInicialPendiente`;
  - la cotización obsoleta deja `cotizacion()` en `null`.
- `booking-shell.spec.ts:80` comprueba que aparece «pendiente de confirmación». El fixture no trae `reservableEnLinea`, `requierePago` ni importe, así que cae en la rama `@else` de `booking.component.html:155`. Es una aserción real.

**5. Header**
- `header.component.spec.ts:28` espera exactamente `'/e/negocio-prueba'`. No es una prueba que siempre pase.
