# 003 — Persistencia de horarios locales y creación UTC

Autor: Codex. Se leyeron PROTOCOLO.md, ESTADO.md y la revisión 003 completa. Sin commit ni despliegue.

## Corrección

Se retiró `spring.jpa.properties.hibernate.jdbc.time_zone: UTC` de `application.yml`. Se conservaron `serverTimezone=UTC`, `forceConnectionTimeZoneToSession=true` y el converter `FechaUtcPersistencia` de `CitaEntidad.creadaEn`, sin cambios.

La prueba con MySQL real detectó una diferencia relevante con la propuesta inicial: **quitar solo la propiedad global deja una cita local de 10:00 almacenada como 16:00**, aunque al releerla desde Hibernate vuelva a 10:00. La ida/vuelta sola oculta el desplazamiento en SQL. No se consideró suficiente ese resultado.

Se verificó primero de forma aislada y después se habilitó `hibernate.type.java_time_use_direct_jdbc: true`. Hibernate entrega los tipos locales de Java directamente a JDBC, conservando el valor de horarios TIME/DATETIME. La creación sigue pasando por su converter Timestamp UTC y por la sesión UTC de MySQL. Esta es una corrección de representación/persistencia necesaria para cumplir la regresión solicitada; no cambia las reglas de horarios, disponibilidad, precios, RBAC ni tenant.

## Pruebas

- `CitaCreacionUtcRepositorioTest`: ya no configura `hibernate.jdbc.time_zone`. Comprueba la lectura del UTC escrito mediante el converter, incluso en una sesión H2 con otra zona. La comprobación de almacenamiento SQL UTC se cubre específicamente con MySQL, evitando confundir los tipos de fecha de H2 con el driver real.
- `HorariosZonaJvmRepositorioTest`: cambia temporalmente la zona predeterminada de la JVM a America/Mexico_City, lee una regla SQL de 09:00 como 09:00, escribe/relee cita de 10:00 (también comprueba hora SQL) y relee creación UTC. Restaura la zona en finally y utiliza aislamiento de JUnit.
- `HorariosZonaJvmMysqlTest`: usa el driver MySQL con la misma configuración JPA de `application.yml` y las opciones de conexión UTC conservadas. Con JVM America/Mexico_City comprueba regla 09:00/19:00, cita 10:00/10:30, creación UTC 16:45:12, sesión SQL UTC y horas SQL 10 para inicio y 16 para creada_en. Se habilita por variables FLUORA_REGRESION_MYSQL_URL/USER/PASSWORD, sin credenciales incrustadas en la prueba.
- La prueba MySQL crea **solo tablas TEMPORARY** generadas desde los mapeos, en una única conexión que las oculta únicamente dentro de esa sesión; creada_en usa TIMESTAMP como en las migraciones. No usa create/update/drop de Hibernate sobre las tablas del negocio. Al cerrar la conexión desaparecen las tablas temporales. No requiere migración.
- Las pruebas cargan las propiedades JPA reales desde `application.yml` y comprueban que no vuelva a aparecer `hibernate.jdbc.time_zone`.

La primera aproximación H2 con sesión UTC interpretaba TIME según su propia semántica; se ajustó el fixture H2 y se añadió MySQL para verificar el contrato real. También se corrigió la inicialización del proveedor de conexión del fixture MySQL antes de la verificación completa.
